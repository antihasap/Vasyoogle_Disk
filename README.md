1. Описание проекта: В рамках курсового проекта разрабатывается клиент-серверная система «Распределенный файловый менеджер» (Distributed File Manager, DFM), предназначенная для организации хранения, синхронизации и обмена файлами между пользователями. Сервер ведет строгий учет всей активности.

2. Бизнес-требования

• Проблема: Существующие коммерческие облачные решения (Dropbox, Google Drive) часто ограничены корпоративными политиками безопасности, требуют постоянного интернет-соединения с внешним миром и не позволяют развернуть изолированное независимое хранилище внутри локальной сети учебного заведения. Синхронизация файлов через съемные носители или мессенджеры замедляет рабочий процесс и приводит к дублированию информации.

• Обоснование и практическая значимость проекта:
1) Создание независимого, контролируемого и безопасного локального хранилища данных.
2) Снижение нагрузки на внешние интернет-каналы за счет локализации трафика внутри сети.
3) Автоматизация учета активности пользователей и ведение строгой аналитики использования дискового пространства.
4) Практический опыт проектирования клиент-серверной архитектуры и разработки кастомных сетевых протоколов.
5) Закрепление навыков работы с конкурентными запросами, пулами потоков (Threading/Asyncio) и изоляцией транзакций в БД.
6) Успешная защита курсового проекта и формирование фундаментального портфолио в области системного программирования.
   
3. Пользовательские требования
   
• Пользователь должен иметь возможность пройти регистрацию (AUTH) и авторизацию в системе по уникальному имени и паролю.

• Пользователь должен иметь возможность просматривать актуальный список (LIST) всех доступных для скачивания файлов на сервере.

• Пользователь должен иметь возможность загружать (UPLOAD) файлы со своего локального устройства в облачное хранилище сервера.

• Пользователь должен иметь возможность скачивать (DOWNLOAD) любые доступные файлы из хранилища на свое локальное устройство.

• Пользователь должен иметь возможность удалять (DELETE) собственные загруженные файлы.

• Пользователь должен иметь возможность запрашивать качественную и количественную статистику (STATS) по работе системы и своей активности.

4. Функциональные требования

Группа 1. Архитектура взаимодействия и управление профилем (ФТ-1)
```text
ФТ-1.1. Авторизация и сессии (AUTH): При первом запуске клиента пользователь выполняет вход или регистрацию. Сервер проверяет соответствие пары логин/пароль с хэшированными данными в БД. В случае успеха клиенту присваивается активная сессия.
ФТ-1.2. Просмотр директории (LIST): По запросу клиента сервер обращается к базе данных, формирует список доступных файлов с указанием их авторов, размеров и даты загрузки, после чего отправляет структурированный ответ клиенту для вывода на экран.
ФТ-1.3. Универсальность интерфейсов: Сервер должен обрабатывать запросы независимо от типа интерфейса. Система включает в себя два типа клиентов:
  CLI-клиент — консольное приложение для работы через командную строку.
  Веб-клиент — легковесная HTML-страница для удобного взаимодействия через браузер.
```
Группа 2. Файловые операции и сетевой протокол (ФТ-2)
```text
ФТ-2.1. Сетевое взаимодействие: Обмен данными строится по схеме «Запрос — Ответ». Если взаимодействие реализуется через сырые TCP-сокеты, каждый пакет должен строго соответствовать формату: [Длина заголовка (4 байта)][Тип команды (2 байта)][Тело данных / Payload].
ФТ-2.2. Загрузка файла (UPLOAD): Клиент инициирует передачу файла, отправляя метаданные (имя, размер). Сервер проверяет наличие свободного места, создает запись в БД и принимает файл по байтовому потоку, сохраняя его в директорию storage/ под уникальным именем (UUID) во избежание конфликтов имен.
ФТ-2.3. Скачивание файла (DOWNLOAD): Клиент передает ID файла. Сервер проверяет его существование, находит физический UUID-путь на диске, считывает файл и транслирует его клиенту, одновременно фиксируя операцию в системном логе.
ФТ-2.4. Удаление файла (DELETE): Пользователь может отправить запрос на удаление. Сервер проверяет права доступа: удалять файлы разрешено только их владельцам (owner_id). При подтверждении прав файл стирается с диска, а запись в БД аннулируется.
ФТ-2.5. Контроль целостности: При загрузке и скачивании система обязана рассчитывать контрольную сумму файла (MD5 или SHA-256) для подтверждения отсутствия потерь и битых байтов при передаче по сети.
```
Группа 3. Параллельная обработка и логирование (ФТ-3)
```text
• ФТ-3.1. Многопоточность сервера: Сервер не должен блокироваться при обработке длительных операций. При подключении нового клиента сервер обязан выделять под него отдельный поток (Threading) или асинхронную задачу (Asyncio). Быстрые запросы (LIST, AUTH) от одних пользователей должны обрабатываться мгновенно, даже если в этот момент другие пользователи загружают тяжелые файлы (от 1 ГБ).
• ФТ-3.2. Логирование активности: Все ключевые события (подключения, ошибки, сетевые команды) сервер параллельно с базой данных записывает в текстовый файл server.log в формате: [YYYY-MM-DD HH:MM:SS] [Тип события] Сообщение.
```
Группа 4. Учет статистики и аналитика (ФТ-4)
```text
По команде STATS система должна собирать и выводить в отдельном окне/интерфейсе аналитические показатели, разделенные на две категории:
• ФТ-4.1. Количественные показатели (Метрики):
	• Общее число зарегистрированных пользователей.
	• Общее количество хранящихся файлов и их суммарный вес в ГБ.
	• Счетчик скачиваний для каждого файла (выделение Топ-1 популярного).
	• Текущее количество активных сетевых сессий (онлайн-нагрузка).
	• Средняя скорость передачи данных при операциях UPLOAD/DOWNLOAD.
• ФТ-4.2. Качественные показатели (Аналитика):
	• Определение самого активного пользователя (лидер по объему или количеству загрузок).
	• Распределение файлов по категориям (например: Документы — 30%, Изображения — 40%, Видео — 30%) на основе анализа расширений файлов.
	• Выявление «мертвого груза» — файлов, которые были загружены, но ни разу не скачивались.
	• Определение пиковых часов нагрузки на сервер по логам скачиваний.
```

5. Системные ограничения
   
  1\. Технологические ограничения

• Язык реализации — C++.

• Разработка ведется на — Windows / Linux (рабочие машины команды).

• Исходный код хранится в — Git, платформа — GitHub.

  2\. Ограничения по хостингу

• Режим работы — серверная часть должна работать круглосуточно (24/7).

• Бюджет проекта — 0 рублей.

  3\. Ограничения по данным

• Хранение метаданных — SQLite.

• Хранение физических файлов: На сервере создается папка storage/. Чтобы избежать конфликтов имен (если два пользователя загрузят report.pdf), файлы сохраняются под уникальными именами (UUID), а оригинальное имя хранится в БД.

• Логирование: Параллельно с БД сервер может писать текстовый лог server.log (кто зашел, что скачал, какие ошибки).

  4\. Ограничения по срокам

• Срок сдачи — проект должен быть завершен и готов к защите к концу первого семестра.

  5\. Ограничения по нагрузке и доступности

• Целевая аудитория — студенты и преподаватели учебной группы / кафедры.

• Время отклика сервера — на быстрые запросы (авторизация, список файлов) не более 0.5 секунд.

• Требуемая доступность — 24/7 в рамках локальной сети вуза.

  6\. Ограничения по интерфейсу

• Взаимодействие пользователя с системой — через два независимых интерфейса: консольный CLI-клиент и легковесный Веб-клиент (HTML/CSS страница). Смежные сторонние приложения не используются.

6. Нефункциональные требования для Распределенного файлового менеджера:

• Производительность и отказоустойчивость: Система должна корректно обрабатывать конкурентные запросы и выдерживать до 50 одновременно активных клиентов без деградации скорости отдачи мелких пакетов (команды LIST, AUTH). Сервер не должен блокироваться или «зависать» для остальных пользователей во время долгой загрузки (UPLOAD) или скачивания (DOWNLOAD) тяжелого файла (объемом от 1 ГБ) одним из клиентов.

• Надежность и резервное копирование: Доступность файлового менеджера — не ниже 99%. При аварийном завершении процесса сервера время его перезапуска и восстановления связи с БД не должно превышать 15 секунд. Резервное копирование базы данных db.sqlite и лог-файлов должно производиться автоматически раз в сутки.

• Безопасность и целостность данных: Вся передача файлов и метаданных по сети должна сопровождаться проверкой контрольных сумм (MD5 или SHA-256) на стороне клиента и сервера для гарантированной защиты от потери байтов. Доступ к операциям удаления (DELETE) строго разграничен — пользователь имеет право удалить только тот файл, владельцем которого он является (проверка по owner_id). Для предотвращения DDoS-атак и спама сокетов вводится ограничение — не более 30 сетевых запросов в минуту от одного клиента.

• Интерфейс: Консольный клиент (CLI) должен обладать интуитивным меню команд со встроенной справкой (help). Веб-интерфейс должен быть адаптивным, кроссбраузерным и позволять загружать файлы простым перетаскиванием (Drag-and-Drop) или через стандартную форму выбора файлов.

• Архитектура и код: Исходный код сервера и клиента должен быть модульным, разделенным на логические слои (сетевой уровень, уровень бизнес-логики, уровень работы с БД/диском). Обязательно ведение сквозного логирования в файл server.log с фиксацией времени, IP-адреса клиента и типа операции. Проект должен содержать базовую техническую документацию по развертыванию и схему структуры базы данных.
